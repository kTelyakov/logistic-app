# Design

## Context

Тесты опираются на `e2e-foundation` и экран. Юнит-тесты пишутся вместе с кодом в своих changes (ядро `seq` в `sync-core`, команды в `decisions-and-commands`), здесь фиксируются перечень и критерии. См. proposal.md.

## Goals / Non-Goals

**Goals:**
- Каждое требование 2-8 покрыто сценарием, как в колонке «Проверка» задания.
- Сценарии быстры настолько, насколько позволяют условия задания (5 минут для drop/dup/reorder неизбежны).

**Non-Goals:**
- Покрытие каждой ветки UI.

## Decisions

- **Два набора:** `make e2e` (B1-B18) и `make e2e-stress` (C1-C3), чтобы основной прогон оставался предсказуемым по времени.
- **Ускорение времени там, где можно:** сдвиг серверных таймеров (`reset` раз в 2 минуты, истечение решений) через переменные окружения заглушки; 5-минутный прогон drop/dup/reorder остаётся реальным по заданию.
- **Подмена часов браузера через `page.clock`** для B12; сервер при этом работает в реальном времени.
- **Сообщения об ошибках проверяются по `data-testid`**, а не по тексту, чтобы не ломаться при смене формулировок.
- **Фоновая вкладка (C3):** открыть вторую страницу и вернуться; проверка догона через сверку.

## Risks / Trade-offs

- [Нестабильность 5-минутного сценария] → фиксированный `FAULT_SEED`, сверка по `expect.poll`, перезапуск только падения, не набора.
- [WebGL в headless Chromium (SwiftShader) медленный] → флаги GPU в конфигурации Playwright; C2 сравнивает отзывчивость, а не FPS.
