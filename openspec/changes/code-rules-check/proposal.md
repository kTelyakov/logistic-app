# Proposal

## Why

Часть 3 задания: правила кода 1–3 проверяет `make check` автоматически, вместе с `vue-tsc` и линтером; нарушение это ошибка, а не предупреждение. На разборе проверяющие вносят нарушение каждого правила и ждут, что `make check` его поймает. Агент, который пишет код, не должен иметь возможности незаметно нарушить границы модулей.

## What Changes

- ESLint (flat config) с `typescript-eslint` и `eslint-plugin-vue`; все правила уровня `error`.
- Локальный плагин `tools/lint` с правилами:
  - правило 1: границы модулей (импорт между модулями только через `index.ts`, `shared` не знает о модулях, модули не знают о `app`);
  - правило 2: компонент не делает запросов и не трогает store (импорты `api/`, store, HTTP, вызовы `fetch`, `*Mutator`);
  - правило 3: HTTP и сеть только в слое `api` через общий клиент; слои `helpers`, `utils`, `api` не тянут лишнего;
  - правило 4: `defineStore` только в `store/`, мутирующие функции store с суффиксом `Mutator`.
- Проверка циклов импортов (граф файлов и модулей по TypeScript API).
- `v-html` запрещён.
- Тесты: на каждое правило есть нарушение, которое проверка обязана поймать, и допустимый код, который ловить нельзя.
- `make check` = `vue-tsc` + ESLint + циклы.
- Существующий код приводится в соответствие правилам; найденные нарушения исправляются.

## Impact

- Новые `eslint.config.js`, `tools/lint/`, зависимости ESLint; `make check` и `AGENTS.md` (ссылки на проверки вместо «появится»).
- Возможны правки существующего кода по найденным нарушениям.

## Non-Goals

- Проверка семантики «бизнес» против «техническое» в теле функции: проверяются слои и импорты, а не смысл.
- Форматирование (prettier).
