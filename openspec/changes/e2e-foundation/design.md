# Design

## Context

`mock-server` даёт `/debug/state`, `FAULTS` и `FAULT_SEED`. Экран появится позже, поэтому основа проверяется на «заглушке экрана» (тестовая страница, умеющая показывать данные из API) и негативными контролями. См. proposal.md: зачем отдельный change.

## Goals / Non-Goals

**Goals:**
- Один хелпер сверки, который вызывают все сценарии.
- Тесты изолированы и воспроизводимы.

**Non-Goals:**
- Реальные сценарии экрана.

## Decisions

- **Заглушка стартует как дочерний процесс на случайном порту внутри фикстуры теста (worker-scoped, перезапуск per test):** изоляция дороже по времени, но исключает общее состояние; время запуска заглушки небольшое.
- **Сверка читает экран через стабильные `data-testid` и атрибуты данных**, а не через визуальный текст: это контракт между экраном и тестами, фиксируется в `AGENTS.md` (атрибуты `data-testid` не удаляются).
- **Сравнение нормализует порядок и форматирование:** сортировка по id, время сравнивается как момент, а не как строка в поясе площадки.
- **Допуск на гонку:** `expectScreenMatchesServer()` ждёт сходимости до таймаута (`expect.poll`), потому что экран догоняет сервер асинхронно; расхождение после таймаута и есть ошибка.
- **`blockExternal` на уровне `context.route`**, а не `page.route`: покрывает воркеры и новые вкладки.

## Risks / Trade-offs

- [Сверка по DOM хрупка при редизайне] → `data-testid` как стабильный контракт.
- [Допуск на сходимость скрывает постоянную задержку] → отдельный порог времени сходимости в сценариях синхронизации.
- [Запуск заглушки на каждый тест замедляет прогон] → фикстура переиспользует процесс для тестов с одинаковым окружением, если есть сброс состояния (`POST /debug/reset`); решение уточняется в реализации.

## Open Questions

- Нужен ли `POST /debug/reset` в заглушке или достаточно перезапуска процесса (не меняет спеки).
