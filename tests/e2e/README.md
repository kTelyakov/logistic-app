# E2E: основа

Playwright против заглушки. Здесь описаны фикстуры, хелперы и контракт, по которому тесты
читают экран. Сценарии по требованиям задания (B1–B18) пишутся поверх этой основы.

## Запуск

```
make install      # npm install и Chromium для Playwright
make e2e          # весь набор
E2E_CHANNEL=chrome make e2e   # на установленном Google Chrome (настоящий GPU для WebGL)
```

На macOS 13 Playwright не ставит свой Chromium: `make install` повторяет установку с
`PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=mac14-arm64`. Если и это не работает, используйте `E2E_CHANNEL=chrome`.
Встроенный Chromium рисует WebGL программно (SwiftShader), цифры FPS на нём заниженные.

## Фикстуры (`fixtures/index.ts`)

| Фикстура | Что делает |
|---|---|
| `mock` | Свежая заглушка отдельным процессом (`node --import tsx mock/src/main.ts`, `PORT=0`) на свободном порту. Останавливается после теста. Порты и состояние тестов не пересекаются |
| `mockEnv` | Окружение заглушки: `test.use({ mockEnv: { FAULTS: 'slow', ROLE: 'observer' } })`. Переменные окружения разработчика в заглушку не попадают |
| `appKind` | `'real'` (по умолчанию, собранный экран через `vite preview` на 5199) или `'reference'` (эталонный экран, проверка самой основы): `test.use({ appKind: 'reference' })` |
| `appOrigin` | Адрес, с которого отдаётся экран |
| `app` | Страница с открытым экраном, подключённым к `mock` |
| `externalGuard` | Включена автоматически: запросы вне экрана и заглушки блокируются, а тест, который к ним обратился, падает в конце |
| `allowExternal` | `test.use({ allowExternal: true })` для тестов самой защиты |

`mock` умеет: `debugState()`, `pause()`, `resume()`, `stop()`, `output()` (лог процесса), `url`, `port`.

## Сверка экрана с сервером

```ts
await expectScreenMatchesServer(app, mock)
```

Каждый сценарий заканчивается этим вызовом. Хелпер:

1. ставит симуляцию заглушки на паузу (`POST /debug/pause`): в живом режиме сервер меняется быстрее, чем экран успевает за ним;
2. ждёт, пока `seq` экрана сравняется с `seq` сервера (при отказах экран догоняет повторным снимком);
3. строго сравнивает машины, пункты, очереди и решения с `/debug/state`;
4. возобновляет симуляцию, в том числе когда сверка упала.

Расхождение выводится по полям: `decision d-3381 status: экран="pending" сервер="executed"`.
`diffStates()` — чистая функция, покрыта юнит-тестами на каждый вид расхождения (`helpers/diff.test.ts`).

## Контракт экрана для тестов

Экран обязан выставлять это, и **`data-testid` и `data-*` ниже нельзя переименовывать и удалять**:

| Что | Как |
|---|---|
| Последний применённый `seq` | `window.__dispatch.seq()` |
| Машины | `window.__dispatch.vehicles()` → `[{ vehicle_id, state, x_m, y_m, last_seen }]`. Схема рисуется на canvas, машин в DOM нет |
| Пункт | `[data-testid="point"]` с `data-point-id`, `data-mode` |
| Элемент очереди (внутри пункта) | `[data-testid="queue-item"]` с `data-vehicle-id`, `data-eta`, `data-service-start`, `data-wait-s` |
| Решение | `[data-testid="decision"]` с `data-decision-id`, `data-status`, `data-version` |

Время в атрибутах — ISO 8601; сравнивается как момент, формат отображения для людей не важен.

## Эталонный экран (`reference-screen/index.html`)

Не экран диспетчера. Страница на чистом JS, которая реализует протокол (`seq`, дубли, дыры,
перестановки, `reset`, `heartbeat`) и контракт выше. На ней проверяется сама основа
(`foundation.spec.ts`), независимо от настоящего экрана. Настоящий экран проверяется в `screen.spec.ts`.

## Настоящий экран (`screen.spec.ts`)

Экран собирается и отдаётся как в боевой сборке (`npm run build` и `vite preview`), адрес заглушки передаётся
параметром `?api=`. Проверяется: данные доходят, сверка с `/debug/state` проходит без отказов и с
`drop,dup,reorder`, время в поясе площадки при другом поясе браузера, `reason` с разметкой выводится текстом,
внешних запросов нет.

## Что проверяет `foundation.spec.ts`

| № | Проверка |
|---|---|
| A1 | Заглушка стартует с нужным `FAULTS`/`LOAD`/`ROLE`/`FAULT_SEED`; окружение разработчика не просачивается |
| A2 | `debugState()` не искажается `FAULTS=drop,dup,reorder`, хотя поток искажён |
| A3 | Один `FAULT_SEED` — те же потерянные `seq`; другой seed — другие |
| A4 | Каждый тест получает свежую заглушку; после теста порт закрыт |
| A5 | Сверка проходит на эталонном экране без отказов и с `drop,dup,reorder` |
| A6 | Внешние запросы блокируются и записываются; тест с таким запросом падает; `data:`/`blob:` и адреса экрана и заглушки разрешены |
| A7 | Негативный контроль: испорченный статус решения, элемент очереди, режим пункта, машина — сверка падает и называет поле, а сервер возобновляется |
