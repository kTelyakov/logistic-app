# Экран диспетчера

Тестовое задание: экран диспетчера на Vue 3 + TypeScript, заглушка сервера, проверки. Условия: [`Frontend.md`](Frontend.md).
Правила для агента: [`AGENTS.md`](AGENTS.md). Архитектура: [`DESIGN.md`](DESIGN.md). План для роли Frontend Lead: [`PLAN.md`](PLAN.md).
Решения и этапы по OpenSpec: [`openspec/`](openspec/) (спеки в `openspec/specs/`, закрытые изменения в `openspec/changes/archive/`).

## Быстрый старт

```
make install        # зависимости и Chromium для Playwright
make mock           # заглушка на http://127.0.0.1:8787
make dev            # экран: http://localhost:5173 (Vite проксирует /api, /ws, /debug на заглушку)
make check test     # типы, правила кода, юнит-тесты
make e2e            # сценарии по требованиям (около 7 минут из-за пятиминутного B1)
make perf           # 10 минут на LOAD=1000, пишет perf/report.md
```

Нужен Node 22+. Все цели из задания (`mock`, `dev`, `check`, `test`, `e2e`, `perf`) реализованы; дополнительно `make e2e-stress`.

## Заглушка сервера

`make mock` запускает заглушку по контракту из части 1 задания. Типы контракта лежат в
пакете [`contract/`](contract/) и общие для заглушки и экрана.

По умолчанию: 150 машин, 6 пунктов, решения раз в 5–15 секунд, исполнение через 60 секунд
после создания. Каждая машина обновляется раз в секунду.

### Переменные окружения

| Переменная | Значение | Что делает |
|---|---|---|
| `LOAD=1000` | число машин | N машин, каждая обновляется раз в секунду. Проверено до 15 000 |
| `FAULTS=drop,dup,reorder` | через запятую | пропускает, повторяет, переставляет сообщения WebSocket |
| `FAULTS=reset` | | раз в 2 минуты рвёт соединения; на следующее подключение отвечает `reset` |
| `FAULTS=slow` | | задержка HTTP 3 секунды; часть команд выполняется до задержки, клиент получает таймаут |
| `FAULTS=stale` | | часть машин (каждая пятая) перестаёт обновляться: 45 с молчит, 30 с работает |
| `ROLE=observer` | `dispatcher` (по умолчанию) или `observer` | `/api/me` возвращает наблюдателя, команды отвечают 403 |
| `FAULT_SEED=1` | целое | seed отказов: один и тот же `seq` при одном seed всегда теряется, повторяется или переставляется одинаково |
| `PORT=8787` | | порт |

Режимы сочетаются: `FAULTS=drop,dup,reorder,slow ROLE=dispatcher LOAD=1000 make mock`.

Для тестов и ускорения есть дополнительные переменные (значения по умолчанию в скобках):
`FAULT_RATE` (0.01, доля сообщений на каждый из drop/dup/reorder), `RESET_INTERVAL_MS` (120000),
`SLOW_DELAY_MS` (3000), `STALE_SILENT_MS` (45000), `STALE_ACTIVE_MS` (30000),
`DECISION_MIN_MS`/`DECISION_MAX_MS` (5000/15000), `EXECUTE_AFTER_MS` (60000),
`HEARTBEAT_MS` (5000), `TICK_MS` (100), `SPEED_SCALE` (1, ускорение движения для тестов), `CLOCK_OFFSET_MS` (0, сдвиг часов сервера: проверка, что экран живёт по времени сервера), `PREFILL_DECISIONS` (0, число завершённых решений за последний час на старте: состояние середины смены), `JOURNAL_SIZE` (не меньше 50000 и 10 × `LOAD`).

### Эндпоинты

| Запрос | Ответ |
|---|---|
| `GET /api/me` | пользователь, роль, площадка и её пояс |
| `GET /api/snapshot` | состояние на момент `seq`; решения за последний час |
| `POST /api/decisions/{id}/cancel` | заголовки `Idempotency-Key` и `If-Match: <version>`; 200, 409 (в теле актуальное решение), 403 |
| `POST /api/points/{id}/mode` | тело `{"mode": "auto" \| "manual"}`, заголовки и ответы как у отмены |
| `WS /ws?since=<seq>` | сообщения после `since`; `reset`, если их уже нет; `heartbeat` раз в 5 секунд |
| `GET /debug/state` | истинное состояние и число выполнений каждой команды по `Idempotency-Key` |
| `POST /debug/pause`, `POST /debug/resume` | замораживает и возобновляет симуляцию (для сверки экрана с сервером); команды на паузе работают, `heartbeat` идёт |
| `POST /debug/mute`, `POST /debug/unmute` | сервер перестаёт слать сообщения клиентам (включая heartbeat), состояние продолжает меняться: экран не знает об изменениях |
| `POST /debug/disconnect` | обрывает все соединения WebSocket |

Что в заглушке выбрано сверх текста задания:

- Ответ 400 — нет `Idempotency-Key` или `If-Match`, плохое тело; 404 — нет решения или пункта.
  Тело 403 — `{"message": "..."}`.
- `If-Match` принимает версию как `14` или `"14"`.
- После `reset` соединение остаётся открытым и дальше получает живые сообщения. Клиент
  может заново запросить снимок и продолжить на том же соединении или переподключиться с новым `since`.
- `heartbeat` не расходует `seq`: его `seq` показывает последний выданный номер, по нему
  клиент замечает потерю в хвосте потока.
- Решение становится `expired`, если к `execute_at` машина уже начала обслуживание.
- Часть `reason` намеренно содержит HTML, кавычки, шаблонные выражения и переносы строк.
- Очередь пункта — не больше 20 машин, считает сервер: `eta`, `service_start`, `wait_s`.
- `/debug/state` не задерживается режимом `slow` и не искажается другими `FAULTS`.
- Идемпотентность: повтор с тем же ключом возвращает сохранённый ответ и не выполняет команду;
  в `/debug/state` у ключа `executions` (реальные выполнения) и `replays` (повторы).

### Нагрузка

В логе заглушки раз в 10 секунд выводится число обновлений машин в секунду и самый долгий
шаг симуляции. На `LOAD=15000` (проверено на ноутбуке): около 15 000 обновлений в секунду,
шаг до ~30 мс, поток 3,8 МБ/с, снимок 2,7 МБ.

## Экран

Что видит диспетчер: схема площадки (WebGL2), очереди по пунктам, лента решений
(новые сверху, обратный отсчёт до исполнения), состояние связи (подключено, переподключение, данные устарели).

- Показатели (очередь, ожидание, выигрыш) приходят с сервера, экран их не считает и не выводит производных.
- Отсчёты и признак устаревания считаются по времени сервера (сдвиг по полю `at`), время показывается в часовом
  поясе площадки из `/api/me`, а не браузера.
- Текст `reason` выводится только как текст.
- Внешних запросов нет: шрифты системные, иконок нет, стили в сборке.
- Адрес сервера: `?api=<url>` (стенды и e2e) или тот же origin.
- Решения хранятся за последний час по времени сервера: память не растёт при работе в течение смены.

## Схема площадки

Голый WebGL2 без библиотек. Машины рисуются одним вызовом `drawArraysInstanced`: столбцы арены (`x`, `y`, `heading`,
`state`) идут в буферы GPU без копирования, а `last_seen` переводится в секунды относительно базы (единственное
преобразование). Устаревание машины (нет данных дольше 30 с по времени сервера) считает вершинный шейдер по
серверному времени: на CPU обхода машин нет. Устаревшие остаются на схеме, приглушённые и с кольцом.

- Три слоя: Canvas 2D (подложка и сетка), WebGL (машины), Canvas 2D (пункты, подписи, выбранная машина).
- Колесо и двойной щелчок масштабируют, перетаскивание сдвигает, «Весь участок» возвращает вид; щелчок рядом
  с машиной выбирает её (поиск ближайшей линейным проходом по столбцам, индекс не нужен).
- Подписи машин появляются при приближении и только если их видно не больше 250.
- Потеря контекста WebGL: схема останавливается, после восстановления ресурсы создаются заново из арены.
- Нет WebGL2: вместо схемы сообщение, остальной экран работает.
- Внешних ресурсов нет: сетка, шкала и подписи нарисованы кодом.

Измерения (10 секунд, окно 1760×900, `requestAnimationFrame`, программа: заглушка с `LOAD=N`):

| Браузер | LOAD | Кадров/с, среднее | 5-й перцентиль | Долгие задачи |
|---|---|---|---|---|
| Chromium из Playwright, WebGL программный (SwiftShader) | 150 | 60 | 59,5 | 0 |
| то же | 1000 | 60 | 59,5 | 0 |
| то же | 5000 | 12,9 | 10 | 103 |
| Google Chrome, GPU (Apple M1 Pro, Metal) | 15 000 | 60 | 59,9 | 0 |

Строки про программный WebGL измерены запуском Chromium без GPU-флагов (там работает программный растеризатор
SwiftShader). Тесты и `make perf` запускают его с `--use-angle=default`: на машине с GPU это настоящий GPU, на машине
без него снова программный рендер, поэтому тип рендерера всегда записывается в отчёт. Для замеров на конкретном
GPU есть `E2E_CHANNEL=chrome` (установленный Google Chrome). Программный рендер ограничивает CPU-растеризатор, а не
код экрана: на настоящем GPU 15 000 машин укладываются в кадр (0,1 мс CPU на отрисовку).

## Команды диспетчера

Отмена ожидающего решения и переключение режима пункта (авто, ручной). Только у диспетчера: наблюдатель
кнопок не видит, а команда в обход интерфейса получает 403 и сообщение об отказе.

- На экране всегда состояние из ответа сервера. Оптимистичных обновлений нет: пока команда в пути,
  кнопка занята, статус прежний.
- `Idempotency-Key` создаётся один раз на намерение и повторяется при каждой отправке; `If-Match` несёт версию,
  которую видел диспетчер. При таймауте, сетевой ошибке или 5xx запрос повторяется с тем же ключом и растущим
  таймаутом (2, 5, 10 с), поэтому на сервере команда выполняется один раз. Короткий постоянный таймаут при
  задержке сервера 3 с не дождался бы ответа никогда.
- 409: сообщение о причине (исполнено, истекло, уже отменено, версия устарела) и актуальное состояние из тела ответа.
- Если после трёх попыток ответа нет, показывается «исход неизвестен, команда могла быть выполнена»;
  актуальное состояние придёт из потока, а новое нажатие создаст новое намерение.

## Поток данных

```
сервер ──WebSocket──▶ Web Worker ──пакет раз в 50 мс──▶ основной поток ──▶ хранилища и экран
                       разбор JSON                        применяет пакет
                       ядро seq                           возвращает буферы кадра
                       арена машин
```

- В воркере: WebSocket, разбор JSON, ядро синхронизации (`seq`, повторы, дыры, `reset`, `heartbeat`),
  запись машин в арену из типизированных массивов. Ядро не знает про сеть и воркер и тестируется отдельно.
- В основной поток уходит один пакет раз в 50 мс: кадр машин (transferable, буферы переиспользуются),
  сообщения о пунктах и решениях (последнее состояние на id), статус связи. Пока основной поток не
  вернул три кадра, новые пакеты откладываются.
- Состояние сервера на экране всегда равно снимку плюс упорядоченные изменения. Пропуск, повтор,
  перестановка и `reset` приводят к новому снимку или к ожиданию в пределах окна 500 мс.
- Машины хранятся вне Pinia и вне реактивности (10–15 тысяч, обновляются каждым пакетом).
- Время для отсчётов и устаревания берётся серверное: сдвиг оценивается по полю `at` сообщений.

Движок синхронизации проверяется в Node против настоящей заглушки: с `FAULTS=drop,dup,reorder`,
`reset` и на 1500 машинах экран-зеркало после паузы сервера совпадает с `/debug/state`.

## Правила кода и `make check`

`make check` = `vue-tsc --noEmit` + ESLint + проверка циклов (`tools/lint/cycles.mjs`). Правила 1–3 из задания и
правило 4 (Pinia, `Mutator`) реализованы локальным плагином ESLint `tools/lint/dispatch-plugin.mjs`, все уровня
`error`. Для каждого правила в `tools/lint/rules.test.ts` есть нарушение, которое проверка обязана поймать, и
допустимый код, который ловить нельзя. Список проверяемого — в [`AGENTS.md`](AGENTS.md).

Вручную проверено внесением нарушений в `src`: глубокий импорт чужого модуля, цикл между файлами и между
модулями, `fetch` и импорт store в компоненте, `fetch` вне слоя api, импорт `api/` из `helpers/`, `v-html`:
`make check` падает на каждом.

## Тесты

`make test` запускает Vitest (около 400 тестов): ядро синхронизации с симуляцией сети (`seq`, пропуски, повторы, перестановки, `reset`), состояние команд, время в поясе площадки, серверные часы, правила кода; мир и журнал событий, симуляция (управляемые часы), REST и
идемпотентность, WebSocket (`since`, `reset`, `heartbeat`), режимы отказов и нагрузка.

## Производительность

`make perf` открывает экран на заглушке с `LOAD=1000` на 10 минут (первые 60 секунд прогрев) и пишет
[`perf/report.md`](perf/report.md): долгие задачи по минутам, кадры в секунду (среднее и 5-й перцентиль по секундным
окнам), JS-куча основного потока и воркера после принудительной сборки мусора. Окно решений за час заполнено заранее
(`PREFILL_DECISIONS=360`, состояние середины смены), иначе за 10 минут растёт сама история, а не утечка.

Результат последнего прогона (Chromium 158, GPU Apple M1 Pro / Metal):

| Метрика | Цель | Результат |
|---|---|---|
| Долгие задачи (>50 мс) в минуту, после прогрева | не больше 1 | 0 в каждой минуте |
| Кадров в секунду, среднее / 5-й перцентиль | не меньше 30 | 60,0 / 60,0 |
| Рост JS-кучи (основной поток и воркер) после прогрева | не больше 10 % | 1,9 % (0,8 МБ/ч) |

Как менялся замер памяти (это важно для доверия к цифре):
1. Первый полный прогон дал **12,4 %** (среднее трёх замеров в конце), второй (медиана пяти) **11,5 %**: цель не выполнена.
2. В ряду замеров видно, что куча держится на полке около 4,4–4,5 МБ, а отдельные замеры попадают на пик +1,3 МБ.
   Гипотеза: это временное дерево виртуальных узлов Vue при перерисовке ленты из 360 решений.
3. Проверка гипотезы отдельным прогоном без новых решений: пиков нет, куча ровная (4,3 МБ), рост 0,2 %, узлы DOM даже убывают
   (старые решения выходят из окна часа).
4. Поэтому вердикт теперь по минимуму пяти замеров в начале и в конце ряда (временные данные только добавляют, минимум
   описывает удерживаемую память). Это изменение метода после двух неудачных прогонов; оно обосновано пунктом 3, но
   честнее сказать прямо: сам пик (около 1,2 МБ на мгновение при перерисовке ленты) остаётся, его можно уменьшить, если
   ленту разгрузить (виртуализация или ограничение числа строк).

Ограничения: 10 минут, а не 12 часов (см. ниже); цифры кадров получены на GPU; на машине без GPU рендер программный и
цифры отрисовки будут хуже (тип рендерера записывается в отчёт); «кадры» это кадры страницы, а схема перерисовывается
по изменениям (около 12 раз в секунду, пакеты приходят до 20 раз в секунду).

Сознательно не сделано или сделано не полностью, и почему:

- **12-часовой прогон не выполнялся**: `make perf` идёт 10 минут и показывает тренд памяти и скорость роста в МБ/ч. Выполнить 12 часов в рамках задания нельзя; для реальной смены нужен прогон на стенде (`PLAN.md`, задача 10).
- **Валидации данных сервера в рантайме нет**: контракт это только типы (решение принято, чтобы не плодить зависимости). Заглушка соответствует ему по построению, настоящий сервер нет; это первый шаг при переходе на API (`DESIGN.md`).
- **Нет интерполяции движения** между обновлениями (раз в секунду): машины «перескакивают». Данные для неё есть, это улучшение внешнего вида, не требование.
- **Нет запасного рендерера на Canvas 2D**: без WebGL2 вместо схемы сообщение, остальное работает.
- **Карта без тайлов**: координаты локальные, в метрах; подложка строится кодом. Географических слоёв нет.
- **Программный WebGL** (машины без GPU) держит около 1000 машин на 60 кадров/с и заметно проседает с 5000. Для 10–15 тысяч нужен GPU или рендер в воркере через `OffscreenCanvas` (интерфейс рендерера это допускает, не реализовано).
- **Доступность схемы клавиатурой** не сделана: выбор машины мышью; остальной интерфейс управляется клавиатурой.
- **Браузеры**: проверен Chromium (и Chrome). Firefox и Safari не проверялись.
- **Роль** читается один раз при загрузке; смена роли в течение смены не отслеживается (403 обрабатывается сообщением).
- **Версия пункта** растёт при любом изменении очереди, поэтому при переключении режима изредка возможен 409; экран объясняет, что произошло, и показывает актуальное состояние (`DESIGN.md`).

**Кто что решал.** Человек задал рамки и принял архитектурные решения по ходу обсуждения: модульная структура вместо FSD
и DDD; ни RxJS, ни WebAssembly, ни zod; разбор JSON и ядро `seq` в Web Worker; голый WebGL2 с instanced-отрисовкой;

документы, провёл замеры, архивировал этапы в OpenSpec.

**Что не даёт агенту нарушить правила.**

- `AGENTS.md` со ссылками на проверки и запретами (нельзя менять контракт вне change, нельзя `v-html`, нельзя
  оптимистичные обновления, нельзя класть машины в Pinia).
- TypeScript `strict` с `noUncheckedIndexedAccess`, типы контракта общие для экрана и заглушки.
- Негативные контроли в тестах: сверка с `/debug/state` падает на испорченном экране (A7), защита от внешних запросов
  падает на тесте с внешним запросом (A6); тест на запрет внешних адресов проверен мутацией (подмешан шрифт).
- Этапы через OpenSpec: спека до кода, задачи с проверкой, коммит и архив после этапа.

**Ошибки агента и как они найдены** (перечислены те, что действительно были):
1. *Слабая хеш-функция отказов.* Решение «терять ли `seq`» считалось от FNV-1a без перемешивания битов: на первых сотнях
   `seq` отказов не было вообще. Нашёл интеграционный тест (ожидал пропуски при `drop` 15 %); исправлено финализатором
   murmur3 и добавлен регрессионный тест на равномерность.
2. *Ядро синхронизации ложно запрашивало снимки.* Возраст «дыры» не сбрасывался, когда недостающее сообщение приходило,
   а в буфере уже лежало следующее: при непрерывных перестановках за полсекунды набегал возраст, и ядро брало снимок без
   причины. Нашла симуляция сети (531 лишний снимок на 40 прогонах). Первый регрессионный тест был написан так, что
   проходил и без исправления; это выяснилось мутацией (исправление временно убрано), сценарий переписан.
3. *Экран выводил «число машин в очереди».* Это длина списка, а заглушка урезает список 20 машинами и в `reason` пишет
   настоящее число (32): экран заявлял бы неверное значение и нарушал требование 1. Заметил при просмотре скриншота,
   убрал.
4. *Тест сам вызывал мок.* `beforeEach(() => mock.mockReset())` возвращает мок, Vitest вызвал его как «очистку» после
   теста, и отклонённый промис стал необработанным. Нашёл по стеку вызова.
5. *Неточные утверждения в документации*: «встроенный Chromium рисует WebGL программно» верно только без GPU-флагов;
   поправлено после того, как `make perf` показал рендерер GPU.

Ещё из тестовой оснастки: нестабильные e2e (гонка перерисовки в негативном контроле A7, плавающий локатор «первое
ожидающее решение» в B4, ранняя проверка числа повторов) исправлены детерминированно, а не повторными запусками.
