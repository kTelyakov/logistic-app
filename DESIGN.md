# DESIGN.md

Экран диспетчера: Vue 3 + TypeScript. Один экран на всю смену, до 10–15 тысяч машин. Подробности решений — в `openspec/specs/` и `openspec/changes/archive/`.

## Модули и владельцы состояния

Архитектура модульная, по предметным областям (не FSD и не DDD: структуру и правила задаёт задание). Импорт между модулями только через `index.ts`; проверяет `make check`.

| Модуль | Владеет | Где живёт |
|---|---|---|
| `sync` | потоком данных, связью, серверным временем | воркер: WebSocket, JSON, ядро `seq`, арена; основной поток: `connectionStore` |
| `vehicles` | машинами | арена из типизированных массивов в воркере, копия-кадр в основном потоке **вне Pinia** |
| `points` | пунктами и очередями, режимом | `pointsStore` |
| `decisions` | решениями за последний час, отменой | `decisionsStore` |
| `session` | пользователем, ролью, поясом площадки | `sessionStore` |
| `site-map` | схемой площадки | WebGL2, состояния нет |
| `src/app` | сборкой: применяет пакеты воркера к хранилищам | `AppContainer.vue` |

Контейнеры (`*Container.vue`) делают запросы, держат состояние и ошибки; компоненты берут данные из props и сообщают через `emit`. Поэтому prop drilling нет: у каждого блока свой контейнер, который читает свои хранилища. Контракт сервера общий для экрана и заглушки: пакет `contract/`, только типы.

## Снимок и изменения, время

Состояние экрана это снимок сервера плюс упорядоченные изменения по `seq`. Ядро синхронизации (`sync/core`) детерминированный автомат без сети и таймеров, он проверен симуляцией 360 случайных потоков с пропусками, повторами, перестановками, обрывами и `reset`.

- Повтор (`seq` не больше применённого) игнорируется. Опережающее сообщение ждёт в буфере окно перестановки (500 мс); не дождалось: новый снимок. Потеря в хвосте потока видна по `heartbeat`.
- Пока грузится снимок, новое копится и применяется после замены состояния: старое и новое не смешиваются.
- Обрыв соединения: подключение с `since` последнего применённого, с нарастающей паузой. Ответ `reset`: новый снимок.
- Воркер шлёт основному потоку один пакет раз в 50 мс (кадр машин как transferable, изменения пунктов и решений, статус). `seq` пакета всегда соответствует его содержимому; при трёх невозвращённых кадрах пакеты откладываются целиком.
- Время для отсчётов и признака «устарела» только серверное: сдвиг оценивается по полю `at` сообщений (наименьшая задержка из замеров). Время показывается в поясе площадки из `/api/me`, не браузера.
- Команды: `Idempotency-Key` один на намерение и на все повторы, таймаут растёт (2, 5, 10 с), `If-Match` версии, которую видел диспетчер. Оптимистичных обновлений нет: показывается ответ сервера, в том числе тело 409.

## Как рисуется схема и почему

Голый WebGL2, один `drawArraysInstanced` на все машины. DOM или SVG на объект при 15 000 машин с обновлением раз в секунду не годятся, Canvas 2D на объект упёрся бы в CPU.

- Машины лежат в арене (структура массивов: `x`, `y`, `heading`, `state` и др.), слот на машину; столбцы идут в буферы GPU как есть, единственное преобразование это `last_seen` в секунды относительно базы.
- Устаревание (нет данных дольше 30 с по времени сервера) считает вершинный шейдер по униформе серверного времени: CPU не обходит машины. Устаревшие остаются на схеме, приглушены, с кольцом.
- Три слоя: Canvas 2D (подложка), WebGL (машины), Canvas 2D (пункты, подписи, выбранная). Подложка и подписи рисуются кодом: внешних ресурсов нет.
- Выбор машины: линейный проход по столбцам (десятки микросекунд), пространственный индекс не нужен. Потеря контекста WebGL: ресурсы создаются заново из арены.
- Измерено: 15 000 машин, 60 кадров/с на GPU (Chrome, Metal), 0,1 мс CPU на кадр; на программном WebGL комфортно до нескольких тысяч (см. `README.md`, `perf/report.md`).

## Что изменится при переходе с заглушки на настоящий API

Контракт описан типами вручную, без проверки в рантайме: заглушка ему соответствует по построению, сервер нет.

1. **Проверка границы.** Первое, что стоит добавить: валидацию снимка и ответов команд на входе (схемы из тех же типов) и счётчик отклонённых сообщений. Сейчас неизвестный `type` просто игнорируется.
2. **Реальные задержки и порядок.** Заглушка упорядочена, настоящий поток нет. Окно перестановки, пауза между снимками, размер журнала на сервере и ёмкость буфера придётся подобрать по записи реального трафика; проверка: воспроизвести запись против ядра.
3. **Снимок большого размера.** 15 000 машин это около 3 МБ JSON; при росте нужны сжатие, пагинация или бинарный протокол. Структура «арена и кадр» это переживёт, меняется только разбор в воркере.
4. **Права и сессия.** Роль берётся один раз из `/api/me`; нужна повторная проверка и обработка смены роли в смене (сейчас 403 обрабатывается сообщением).
5. **Версионирование сущностей.** `version` пункта растёт при любом изменении очереди, поэтому `If-Match` режима бывает устаревшим чаще, чем хочется; возможно, серверу нужна отдельная версия режима.
6. **Время.** Если сервер отдаёт `at` только в части сообщений, оценка сдвига опирается на `heartbeat` и снимок; проверить на реальной частоте.
7. **Адреса.** Сейчас `?api=` или тот же origin с прокси Vite; в проде это конфигурация окружения.
